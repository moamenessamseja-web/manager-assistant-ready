## 1. Fix chat command understanding — highest priority

The application's central selling point is that a business owner can speak or type naturally and have the app automatically distribute the resulting transactions to the correct accounts and screens.

Currently, command understanding remains inadequate both offline and with Gemini configured.

Investigate the real command-processing pipeline, including the chat screen, assistant controller, Gemini integration, local rules/parser, data models, storage, and business-operation functions.

Improve it so that:

- Typed text and voice transcription use the same processing pipeline.
- Supported commands work without an API key.
- Gemini remains optional and improves interpretation where appropriate.
- Local processing handles supported commands before invoking Gemini.
- Gemini failures never prevent manual entry or destroy saved messages.
- The original message and its processing result are preserved.
- A successful transaction cannot execute twice because of retries.
- Ambiguous financial commands require clarification or confirmation.
- The chat automatically updates the appropriate screens, account balances, and notifications.

Prioritize existing operations: employee attendance, advances, deductions, supplier deliveries, purchases, supplier payments, expenses, reminders, and commitments.

Support common Egyptian Arabic expressions and Arabic-Indic and Western digits. Handle negation, names, amounts, dates, units, and incomplete commands conservatively.

Do not replace existing business logic with a parallel accounting system.

### Expected-delivery example

For a message such as:

"المورد عجمي جاب الآن ٢٠ كيلو سكر"

The system must distinguish a completed delivery from a future commitment. It must not fabricate additional transactions merely because the message mentions multiple names or products.

Inspect the existing models and determine whether the current parser is duplicating operations, confusing entities, or misinterpreting quantities and totals.

For an expected delivery, save the commitment and schedule a local reminder. Do not mark the purchase as completed until receipt is confirmed.

For completed deliveries, update the appropriate supplier and inventory records using existing accounting rules.

Add regression tests for the actual bugs discovered.

## 2. Fix automatic chat memories and reminders

The chat currently appears to create reminders or commitments automatically without reliably respecting the user's intended date or time.

Inspect the memory, reminder, commitment, date-parsing, and notification code.

Distinguish clearly between:

- A conversational fact or note.
- A reminder explicitly requested by the user.
- A future commitment or expected delivery.
- A completed business transaction.

Do not automatically turn every statement into a scheduled reminder.

For example:

- "افتكر أدفع الإيجار يوم ٢٠ أكتوبر الساعة ٩ صباحًا" should create a reminder for the specified time.
- "هجيب بضاعة بكرة" should create a commitment only if the existing business rules support it and the required information is sufficiently clear.
- A vague statement without a reliable date must not silently receive an arbitrary date or time.

Ask a concise clarification when a required date, time, person, or amount is ambiguous.

Use the device's local timezone consistently. Handle Arabic date expressions, relative dates, and time formats carefully.

Persist scheduled reminders locally and avoid duplicate notifications after editing, rescheduling, or restarting the application.

Do not confuse the app's Memory screen with scheduled reminders. Inspect how both features are currently implemented before modifying either.
